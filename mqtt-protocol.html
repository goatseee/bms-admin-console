BMS管理系统 — MQTT接口协议文档

基于 EMQX 5.7.2 Broker + MQTT 5.0 协议标准，定义 BMS 设备端与平台端的完整通信协议
协议版本 V2.0 更新日期 2026-10-08 适用对象 设备端固件 / 平台服务端 消息格式 JSON（UTF-8）

1. 概述

1.1 文档目的与适用范围

本协议定义了 BMS（电池管理系统）设备端与管理平台之间的 MQTT 通信接口。设备端为嵌入式硬件板子，通过 MQTT 5.0 协议接入 EMQX 5.7.2 Broker；平台端通过 共享订阅 消费设备消息，并通过 请求-响应模式 向设备下发控制指令。

支持的通信内容：电池实时数据、开关状态、单体电压、GPS 定位、告警故障、OTA 升级、远程控制（锁定/重启/休眠/参数配置等）。

1.2 EMQX 5.7.2 系统架构

BMS 平台采用 EMQX 5.7.2 作为 MQTT 消息中间件，整体架构如下：

2.2 监听器配置

EMQX 5.7.2 通过 HOCON 配置文件（etc/emqx.conf）或 Dashboard 配置监听器：

# ===== 监听器配置（emqx.conf 节选）=====
listeners.tcp.default {
  bind = "0.0.0.0:1883"            # 设备 TCP 接入（生产环境建议仅内网/专线）
  max_connections = 1024000
}
listeners.ssl.default {            # 设备 TLS 接入（生产推荐）
  bind = "0.0.0.0:8883"
  ssl_options {
    certfile   = "/etc/emqx/certs/server.pem"
    keyfile    = "/etc/emqx/certs/server.key"
    cacertfile = "/etc/emqx/certs/ca.pem"
    verify     = verify_none        # 双向认证时改为 verify_peer + fail_if_no_peer_cert
  }
}
listeners.ws.default { bind = "0.0.0.0:8084" }   # 平台 WebSocket 调试接入
listeners.wss.default { bind = "0.0.0.0:8085" }  # WSS 加密接入
# QUIC 监听（可选，5.7 支持 MQTT over QUIC）
listeners.quic.default { bind = "0.0.0.0:1453" }

2.3 集群模式

生产环境采用 3 节点静态集群，EMQX 使用内部分布式 DB（DBT）在节点间同步路由表，任意节点可处理任意设备的消息路由：

# emqx.conf 集群配置
node {
  name   = "emqx@10.0.0.1"        # 每节点唯一
  cookie = "bms-emqx-cookie-2026" # 集群共享 cookie
}
cluster {
  name = "bms-emqx-cluster"
  discovery_strategy = static     # 静态节点列表发现
  static.seeds = ["emqx@10.0.0.1", "emqx@10.0.0.2", "emqx@10.0.0.3"]
}
zone.external = {                 # 设备接入区
  mqtt.max_topic_alias = 16
  mqtt.retain_available = true
}
设备端连接任意节点均可收发消息（路由自动转发）；平台端建议通过负载均衡（如 Nginx TCP 代理 / EMQX LB）连接集群，避免单点。RPC 端口 5370、集群发现端口 5380 需在节点间开放。

2.4 MQTT 会话持久化（RocksDB）

EMQX 5.x 使用 RocksDB 本地嵌入式存储持久化 MQTT 会话（会话、订阅、QoS 1/2 消息、遗嘱、保留消息）。设备端可通过 Session Expiry Interval 控制会话生命周期：

# EMQX 5.0 ~ 5.6 配置
durable_sessions = true
# EMQX 5.7+ 配置（5.7 起由 durable_sessions 迁移至 session_persistence）
session_persistence {
  enable = true        # 开启会话持久化（默认开启）
}

BMS 会话策略

场景Session Expiry（秒）说明
正常在线设备300掉线后 5 分钟内恢复会话，离线期间的 QoS 1/2 下行指令不丢失
休眠设备7200休眠 2 小时内唤醒，保留订阅与离线指令
OTA 升级设备1800升级重启期间保留会话，防止重启后指令丢失
已注销/报废设备0Session Expiry=0，连接断开即清除会话
RocksDB 数据目录默认 data/rocksdb，建议挂载 SSD 并纳入备份；EMQX 5.7.2 支持 Dashboard 查看各节点持久化存储用量。

3.3 CONNACK 报文属性

属性（MQTT 5.0）属性ID说明
Session Present可变头标志0=服务端新建会话，1=恢复旧会话
Reason Code-0x00=成功；0x8D=ClientID不合法；0x87=未授权；0x89=ClientID被占用；0x9C=请用另一服务端等，详见第10章
Session Expiry Interval0x11服务端协商后的会话过期时间
Assigned Client ID0x12服务端分配的 Client ID（设备未带 ClientID 时返回）
Server Keep Alive0x13服务端要求的 KeepAlive，覆盖客户端值（如 EMQX 下发 120 秒）
Response Information0x1ACONNECT 请求 RequestResponseInfo 时返回的响应主题前缀
Server Reference0x1C重定向提示（负载均衡场景下返回新节点地址）
Maximum Packet Size0x27服务端最大包长限制
Topic Alias Maximum0x22服务端 Topic Alias 上限
Maximum QoS0x24服务端支持的最大 QoS（EMQX 默认2）
Retain Available0x250=服务端不支持保留消息
Wildcard Subscription Available0x28是否支持通配订阅
Subscription Identifiers Available0x29是否支持订阅标识
Shared Subscription Available0x2A0=不支持共享订阅

3.4 认证方式

EMQX 5.7.2 支持多级认证链（Authentication Chain），BMS 平台建议按下表组合：

方式适用设备EMQX 配置说明
用户名 + 密码所有设备（默认）内置DB / MySQL / Redis / HTTPUsername=IMEI，Password=出厂预置 Token
JWT平台接入的第三方服务JWT 认证（HS256/RS256）平台后端签发，携带用户/角色声明
X.509 证书生产高安全场景监听器双向 TLS + 证书认证证书 CN/OU 映射 Client ID

3.4.1 用户名密码（内置 DB / 密码认证）

# Dashboard → 认证授权 → 认证 → 密码认证（内置数据库）
# 或 etc/emqx.conf
authentication = [
  {
    mechanism = password_based
    backend   = built_in_database   # 可选 mysql / postgresql / redis / mongodb / http / ldap
    password_hash_algorithm {
      name = pbkdf2
      mac_fun = sha256
      iterations = 4096
    }
    user_id_type = username
  }
]
密码采用 PBKDF2-SHA256 存储，设备侧将 IMEI + 出厂盐值派生 Token，禁止明文传输。

4.3 共享订阅（$share / $queue）

平台消费端多实例部署时，使用 共享订阅 实现消息负载均衡（一条消息只投递给一个消费者）：

# 共享订阅格式
$share/{group}/{topic}          # 群组共享：组内轮流投递
$queue/{topic}                  # 等价 $share/broker/{topic}，全局共享

# BMS 平台消费端示例（三实例消费电池数据，消息在组内轮询）
$share/bms-platform/bms/device/+/data
$share/bms-platform/bms/device/+/alarm
$share/bms-platform/bms/device/+/heartbeat
# 独立消费者（状态消息需每实例都收到，不能用共享订阅）
bms/device/+/status
重要限制（MQTT 5.0 规范）：
① 共享订阅 不接收保留消息——设备在线状态（status Topic，Retain=true）必须使用非共享订阅，每个消费实例单独订阅；
② 共享订阅不能与主题别名同时使用；
③ $queue/ 是 MQTT 3.1.1 时代的兼容写法，新开发统一使用 $share/。

4.4 主题重写规则（EMQX Topic Rewrite）

EMQX 支持在客户端发布 / 订阅前重写 Topic（正则匹配 + 分组捕获），用于兼容旧固件、多版本协议统一路由：

# emqx.conf — 主题重写规则
rewrite {
  enable = true
  rules = [
    # 旧固件 v1.x：bms/v1/{imei}/xxx → bms/device/{imei}/xxx
    { from = "^bms/v1/([0-9]{15})/([a-z_]+)$",
      to   = "bms/device/$1/$2",
      re   = "^$", action = publish },
    # 下行指令订阅统一化：bms/{imei}/cmd/# → bms/device/{imei}/cmd/#
    { from = "^bms/([0-9]{15})/cmd/([a-z_]+)$",
      to   = "bms/device/$1/cmd/$2", re = "^$", action = subscribe }
  ]
}
规则按声明顺序匹配，命中后停止；重写动作可分 publish / subscribe / all。

4.5 自动订阅（Auto Subscribe）

设备连接成功后，EMQX 可自动为设备建立订阅（免去设备端 SUBSCRIBE 逻辑，节省链路交互）：

# Dashboard → 模块 → 自动订阅
auto_subscribe {
  topics = [
    { topic = "bms/device/${clientid}/cmd/#",  qos = 1 },   # 接收全部下行指令
    { topic = "bms/device/${clientid}/ota/#",  qos = 1 }    # OTA 相关下行
  ]
  use_clientid = true
}
${clientid} 为 EMQX 占位符（也支持 ${username}），订阅动作由 Broker 完成后；若设备侧不依赖自动订阅，可在设备端显式 SUBSCRIBE 同一 Topic（推荐显式订阅，便于固件自检）。

4.6 EMQX 特有 Topic 特性

4.6.1 延迟发布（Delayed Publish）

发布到 $delayed/{delay_seconds}/{topic}，消息将在指定延迟后按原始 Topic 发布。BMS 可用于「延迟下发」场景（如 30 秒后自动锁定）：

# 发布到延迟 Topic
Publish: $delayed/30/bms/device/864114130050099/cmd/lock   QoS=1
# 30 秒后 EMQX 自动发布到原始 Topic：bms/device/864114130050099/cmd/lock

4.6.2 排它订阅（Exclusive Subscription）

Topic 前缀 $exclusive/：同一 Topic 只允许一个订阅者。适用于「在线状态唯一消费」：

SUBSCRIBE: $exclusive/bms/device/+/status

4.6.3 系统主题（$SYS）与 $share 前缀保护

$SYS/ 为 Broker 内部统计主题，$share/、$queue/、$exclusive/、$delayed/ 均为保留前缀，业务 Topic 一律不使用 $ 开头（详见 12.2 系统主题清单）。

5.5 保留消息（Retained）与在线状态

设备在线状态使用 保留消息：新订阅者立刻收到最后一条状态，无需等待设备心跳：

/* PUBLISH — 设备上线（在线状态保留）
   Topic:     bms/device/864114130050327/status
   QoS:       1
   Retain:    true  (EMQX 保留该消息，新订阅即收)
   Message Expiry Interval: 86400s
   Payload: */
{
  "imei": "864114130050327",
  "online": true,
  "channel": "mqtt",
  "ts": "2026-10-08T02:00:00Z"
}

设备异常掉线时，EMQX 发布遗嘱消息（Will）到同一 Topic 并 retain=true：

/* 遗嘱消息（Will）
   Will Topic:   bms/device/{imei}/status
   Will Retain:  true
   Will QoS:     1
   Will Delay:   10 秒（网络抖动 10s 内重连则不发布） */
{
  "imei": "864114130050327",
  "online": false,
  "channel": "will_timeout",
  "ts": "2026-10-08T02:05:30Z"
}
平台消费 status 必须使用非共享订阅（保留消息不进入共享订阅）；且订阅时 No Local、Retain Handling=0 以接收保留消息。

5.6 QoS 0 / 1 / 2 完整流程

QoS 0（心跳）：最多一次

PUBLISH (QoS 0, no ack) ──▶ 丢弃即止，Broker 不确认
适用：心跳（允许丢失的高频消息）

QoS 1（指令 / 数据）：至少一次

PUBLISH(QoS 1, PacketID=1) ──▶ PUBACK(PID=1, ReasonCode=0x00) ◀──
发送方收到 PUBACK 或超时（默认 60s）重发；可能出现重复，需按 msgId / packetId 去重

QoS 2（OTA 指令）：恰好一次（四段握手）

PUBLISH(QoS 2, PID=1) ──▶ PUBREC(PID=1, 0x00) ◀──
PUBREL(PID=1) ──▶ PUBCOMP(PID=1, 0x00) ◀──
任何一段丢失，接收方按“未收到”重发（PID 复用校验）

5.8 请求-响应模式（Request / Response）

下行指令统一使用 MQTT 5.0 内置请求-响应模式，实现指令与响应关联：

// 平台 → 设备（请求）

  Correlation Data = "cmd-20261008-lock-001"

  User Properties  = {msg_type: resp, request_id: cmd-20261008-lock-001}

7. 下行消息（平台 → 设备）

所有下行指令统一使用 MQTT 5.0 请求-响应模式：PUBLISH 携带 Response Topic 与 Correlation Data，设备执行后向 Response Topic 发布响应（Correlation Data 原样带回），平台据此关联超时与重试。指令公共字段：

字段类型必填说明
cmdIdString是指令唯一 ID（UUID / 业务流水）
actionString是指令动作：lock / unlock / restart / sleep / wake / gps_restart / config / fault_clear / ota / sync
paramsObject否指令参数（按 action 不同）
timestampString是下发时间（UTC）
timeoutInteger否响应超时（秒），默认 30
请求-响应约定：
Response Topic：bms/device/{imei}/resp
Correlation Data：UTF-8 编码的 cmdId，设备原样带回
响应载荷：{ "cmdId": "...", "code": 0, "message": "...", "data": {...}, "timestamp": "..." }

8. EMQX 规则引擎配置

8.1 概述

EMQX 5.7.2 规则引擎以 SQL 方式对消息与事件流进行「过滤 + 字段提取 + 转发」，是数据从 Broker 流向业务的桥梁。BMS 典型链路：

设备 PUBLISH ──▶ EMQX 规则引擎(SQL 过滤/映射) ──▶ 动作(Action/Sink)
    bms/device/+/data  ◀──────────────────────┐
                                              ├─▶ 重发布到内部 Topic（如 bms/alarm/soc_low）
                                              ├─▶ Webhook → 平台 API
                                              ├─▶ Kafka → 数据管道
                                              └─▶ MySQL / InfluxDB → 存储

8.2 支持的事件类型

事件SQL 主题写法BMS 用途
消息发布"bms/device/+/data" 或 "bms/device/#"设备上报数据处理（默认 message.publish）
消息确认"$events/message_acked"QoS1/2 消息送达确认统计
消息丢弃"$events/message_dropped"过期/超配额丢包审计
客户端连接"$events/client_connected"设备上线记录
客户端断开"$events/client_disconnected"设备下线记录（与 LWT 互补）
订阅"$events/session_subscribed" / "$events/session_unsubscribed"平台消费者管理
消息重发布"$events/message_published"转发类消息链路

8.3 SQL 语法要点

示例 1：SOC 低电预警（核心示例）

12.3 ACL 授权规则示例

文件 / 内置规则（emqx.conf 或 Dashboard）

# 授权规则（按顺序匹配，首个命中生效）
authorization {
  deny_list = []
  no_match = deny
  sources = [
    { type = built_in_database, enable = true }
  ]
}

# 内置 ACL 表（可 Dashboard 直接维护）
#  设备端：仅允许发布自己的 /bms/device/{imei}/# 上行 & 订阅自己的下行
#  平台端：允许订阅 $share/bms-platform/# 与发布 bms/device/+/cmd/#
#  平台端：允许订阅 $SYS/# 仅监控

HTTP ACL（动态鉴权，推荐）

authorization {
  sources = [
    { type = http
      url = "http://api.bms-system.com/v1/mqtt/acl"
      enable = true
      method = post
      headers = { "content-type" = "application/json" }
      body = json{
        username = "${username}",
        clientid = "${clientid}",
        topic    = "${topic}",
        action   = "${action}"
      }
    }
  ]
}
ACL 判定优先级：黑名单（deny）→ 授权链 sources 按顺序 → no_match 默认 deny。生产建议「白名单 + deny-all」策略。

12.4 Schema Registry（Avro / Protobuf 编解码）

EMQX 5.7.2 Schema Registry 支持 Avro / Protobuf 编解码，配合规则引擎 schema_encode / schema_decode 实现二进制载荷校验与转换（适合固件侧节省带宽）。BMS 可选启用（默认 JSON，如启用则需固化 Schema 版本）：

Protobuf 示例（bms_cell.proto）

syntax = "proto3";
message BmsCell {
    string imei = 1;
    uint32 msg_id = 2;
    int32  total_voltage_mv = 3;
    int32  current_ma = 4;
    uint32 soc = 5;
    repeated uint32 cell_voltages_mv = 6;
    int64  timestamp_ms = 7;
}

规则中使用 schema 函数

-- 解码二进制载荷为 JSON 字段
SELECT schema_decode('bms_cell', payload) AS cell
FROM "bms/device/+/data"
WHERE payload IS NOT NULL
